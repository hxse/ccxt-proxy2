# CFB 模块与独立执行容器集成

## 使用场景与设计初衷

调用方通过 ccxt-proxy2 使用 CFB，但两套 HTTP 服务、两份接口描述及独立配置增加维护成本。CFB 的终端、Wine、原生 hook、唯一执行权和防重发记录具有独立职责，不能因接口合并而合并进其他 SDK 的进程或镜像。

源项目 cn-futures-bridge 保持不变；相关代码、测试和文档复制进入本仓。原配置的账户与站点合入本仓私有 config.toml。原任务编号与本仓已有编号冲突，来源材料按原文归档到 doc/archive/cfb_source；新的正式任务和模块 current spec 独立指导维护，不依赖源仓或聊天。

## 方案对比

保留两个 HTTP 服务需要继续同步两套路由；把 Wine 合入主容器会耦合启动、重启及原生依赖。每次通过 podman exec 执行业务还需要主服务容器取得容器管理权限。

选择同仓两个生产容器，主服务只增加 CFB 路由与轻量 Unix socket 客户端，CFB 容器维护原有服务、队列、journal 和 GUI worker。命令行运维复用同一个协议，不开第二条业务链。

## 取舍结论

固定同机部署，采用一连接一请求的有界 JSON 协议。业务算法、执行顺序和已知提交事实保持不变；HTTP 断开不等于已开始的交易取消。原生版本约束、CSV 优先级、GUI 恢复和验证边界整体迁入。

代理必须覆盖终端 TCP，不能仅设置 Python HTTP 环境变量。CFB 使用独立开关，复用公共 HTTP CONNECT 代理；32/64 位代理库随执行镜像装配，关闭时显式直连。
