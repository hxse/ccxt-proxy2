# 共享缓存基础与生命周期

## 使用场景与设计初衷

现有缓存由 ExchangeManager 创建与关闭，仅启用 TQ 时无法使用。后续 TQ 和维护需要同一路径、同一资源和相同锁，不能由某个交易所重建操作提前关闭。

原 API 只能从 since 读最佳前缀。TQ 需要在官方最新窗口之前补充相连历史，概况需要最新连续片段，不能让路由自行访问 SQL 或猜测片段。

## 方案对比

每个 Provider 新建缓存实例会分散生命周期；把 TQ 纳入 ExchangeManager 又会混淆交易所与存储。由应用持有并注入共享资源，可以保留 Provider 的独立算法。

将 TQ 纳秒全部压成毫秒会丢失精度；把现有 CCXT 全部改为 BIGINT 纳秒会超出其部分合法时间范围。保留各类型的原生整数单位，在跨源排序时使用足够宽的统一表达更稳妥。

## 取舍结论

保留现有类和片段算法，扩展类型化高级入口、schema 升级和共享资源所有权。普通数据仍使用一套重叠合并和尾根筛选；辅助数据业务由对应阶段加入同一模块。
