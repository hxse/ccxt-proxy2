# Podman 构建与私有部署

## 使用场景与设计初衷

项目由个人使用，本机和 VPS 均为 Linux x86_64。开发继续使用宿主机 uv 环境，生产依赖在部署目标的镜像内构建。原 GitHub Actions 自动发布 Docker Hub 和 Compose 构建即启动流程，不再符合这一工作方式。

用户需要按目标组合明确动作：构建、上传、启动，以及随时停止、查看状态和日志。上传可以提前完成而不影响运行服务，单独启动应复用远端已有版本。重复操作应复用相同实例，更新时不能让两个进程同时访问同一 DuckDB；停止不能排在长构建之后，也不能被在途流程撤销。宿主和容器端口统一为 5123，对宿主只绑定 127.0.0.1。

运行配置以本地为默认来源，每次上传都覆盖全部两份文件，避免新镜像意外沿用旧配置。偶尔只更新源码时，用本次命令的显式参数保留远端准备配置，不增加长期配置开关或配置合并规则。

本机与 VPS 的网络条件不同：本地可以将交易所代理关闭，VPS 需要开启。上传阶段只为远端副本打开 Binance/Kraken 的开关，可复用同一份账户和代理地址配置，避免用户反复手改原件；本地容器直接使用用户原值。

## 方案对比

镜像仓库会增加私人项目的发布和凭据维护；上传源码通常比反复搬运完整镜像更小，服务器可保留自己的依赖构建缓存；代价是首次构建耗时和资源占用较高，因此限制编译并行度。容器化开发会改变现有工具链和验证入口，此任务只需要精简运行镜像。

使用 Python slim 多阶段构建，可以在镜像内部编译 CTP 原生依赖；无需将宿主机虚拟环境搬入镜像，也无需 manylinux wheel 分发链路。部署管理使用同一套 Shell 脚本调用 Podman，远端只需 SSH、Podman 和常规系统工具。Python 随运行镜像提供，只在镜像内部执行应用配置校验和就绪检查；不为部署安装宿主 Python 或引入容器管理 socket。

## 取舍结论

保留宿主开发，使用 Podman 和已有 Dockerfile；本地优先 rootless，远端沿用既有登录账号，以单一 deploy 分发显式动作，复用既有生命周期。通过 SSH 上传构建源码、两份运行配置和必要管理代码，分别原子发布上传版本与构建准备版本，按需启动。只清理本项目无用旧镜像及构建层，保护当前依赖和其他项目。配置以私有快照挂载，便于准确识别变更，并在普通启动失败时恢复原实例；显式停止优先于失败恢复，成功后不保留历史版本。数据目录独立持久化，不参与上传或替换。宿主启动不隐式准备依赖，其他已有 CLI 参数直接安全转发。

现有 CCXT 工厂仅设置 httpProxy，当前 SDK 对 HTTPS 目标不会应用该设置，可能导致本应走代理的请求直连。统一使用 proxies 字典可覆盖两种目标协议，并避免同时设置 httpProxy/httpsProxy 导致 SDK 参数冲突。
