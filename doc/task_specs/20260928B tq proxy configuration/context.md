# TQ 代理配置

## 使用场景与设计初衷

同一 VPS 直接连接 TQ 认证服务会超时，通过既有 HTTP 代理可以完成认证并获取行情。用户需要本地保持直连，远端上传时统一开启 Binance、Kraken、TQ 三个代理开关，且不修改本地原件或重复维护代理地址。

## 方案对比

进程级代理环境变量会影响其他 SDK，也不能可靠表达三个独立开关。只代理认证 HTTP 则遗漏行情 WebSocket、SDK 内部异步 HTTP 与项目自有元数据下载。

## 取舍结论

沿用共享的 proxy 地址和现有远端上传副本补丁。TQ 通过自己的开关控制完整网络链路；适配绑定 TQ 调用上下文，保持其他 SDK 的传输配置和服务故障隔离。配置只在启动时读取，变更需要重启生效。
