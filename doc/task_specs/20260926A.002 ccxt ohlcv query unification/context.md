# CCXT OHLCV 查询统一

## 使用场景与设计初衷

since-limit 与 since-latest 已能复用连续缓存，latest-limit 却每次倒序拉取并且不读缓存。三个查询中重复的分页和尾根确认也增加了理解成本。

用户需要保留公开查询语义、真实时间戳重叠与严格错误行为，仅去掉专门后继确认并合理抽象复用。latest-limit 可从最新 S 和固定周期算出起点，再使用同一向后查询基础。

## 方案对比

先读全库最新缓存再一路追到现在，可能请求远超用户窗口的数据。获取 S 后只查询目标窗口能限制工作范围。直接调用公开 since-latest 又会重新取得 S，因此共享接受既定 S 的内部流程。

为支持自然月保留倒序分支会继续维护两种分页。周线以上采用有限单页能力，重点保持周线及以下完整查询可靠。

Kraken Futures 的 SDK 可把 since＋limit 转为有限时间窗口，非空短页并不等于后面没有行情。沿实际末根继续普通含首分页即可处理有进展的短页；若起点过早导致首窗为空，则明确结束，不为上市前场景增加跨空窗搜索或上市日期查询。

## 取舍结论

同时重构三个查询，保留单前缀、含首连接、一次完整回退、预算和修订语义。网络普通尾根一律保守未知，固定历史重复请求不额外追求首次缓存满 N 根。

正常链路直接完成的合法短历史可以返回；不承诺所有数据源的上市前边界都能成功。验证重点是上市后的正常请求可靠，以及无法完成的边界请求明确失败。
