# 后台采集与清理调度

## 使用场景与设计初衷

用户请求已经会积累缓存，后台只需定期代替人工请求预设品种和周期。VPS 停机几天后仍请求同样的一万根，能与旧历史重叠就自然续接，不需要独立恢复算法。

四个周期都保存主连和加权，但默认只利用 5m 主连的响应范围请求映射，并附带 5m 过渡。映射是逐交易日数据，周期列表只选择后台触发来源，不能把它做成四份周期映射。

清理也通过路由进入数据库所属进程，使后台与用户共享完整的验证、锁和事务行为。采集与清理分开维护，由一个小时流程顺序调用。

## 方案对比

本机免鉴权或直接调用路由函数会多出一种运行入口与生命周期耦合。读取现有私有配置中的 HTTP 用户密码登录，可以沿用完整路由能力而不另造特权通道。

逐级试探或依赖概况判断是否达到一万根会增加请求和状态。固定请求一万根并接受合法短历史，足以处理常见停机场景。

每个元数据 HTTP 请求独立取一次可信时间，内部转换和刷新共用它；清理另取本次时间。整轮不要求同一时刻快照，不需要维护跨 HTTP 的可信时间票据。只从 5m 触发映射也减少了重复元数据和取时请求。

## 取舍结论

使用公开 market_data.toml 保存非敏感计划，私有 market_data_client 只引用已有账号。计划只影响脚本，不设置路由默认值或用户请求权限；一轮中继续可独立完成的工作，失败不无限重试。

默认后台只补充 5m 行情实际覆盖范围内的映射，不因日线/周线更长而额外补更早映射。辅助保留十年不是保证首次采满十年，用户仍可独立请求更早的合法范围。
