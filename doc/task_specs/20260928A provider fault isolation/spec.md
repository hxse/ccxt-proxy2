# SDK 故障隔离

## 任务边界

将全体 SDK 成功才开放 HTTP 的启动方式替换为按身份独立启动。TQ、CFB、Binance、Kraken 互不阻断；继续使用 ccxt/交易所/市场/模式 身份，使不同环境和市场也隔离。现有 CTP 身份采用同一启动机制，交易语义保持不变。

修改服务状态、CCXT 注册表失败清理、TQ 工作线程可用性检查、明确网络故障的 HTTP 错误及 readyz。同步受影响 current spec、自动文档描述、用户说明和过时测试。配置字段、白名单、缓存算法、价格处理、业务校验、SDK 请求模式和订单提交/重试规则不变。

不引入运行时配置重载、请求触发初始化、自动重建失败 SDK、进程隔离或通用熔断框架。配置自身非法仍阻止启动；单次业务错误不能使全局应用退出。达到独立启动、故障入口快速拒绝、资源安全关闭及既有回归通过即可交付。

## 任务规范

### 启动与状态

1. 先验证配置快照与后台计划；这些应用级校验失败仍按原契约退出。
2. 每个白名单身份各自启动初始化任务，不在 HTTP 公用线程池长期占用工作线程；一个任务抛错或等待网络不阻止其他任务或 HTTP 开放。CFB 仍只创建 HTTP 客户端，不增加启动探测或登录。
3. 身份状态统一为 initializing、ready、failed、stopped，由 ServiceRuntime 持有唯一状态；initialized 列表是 ready 身份按白名单顺序生成的视图。初始化完成顺序不必等于白名单顺序。
4. 应用 ready 表示基础生命周期已建立，可以接收请求，不要求全部 SDK ready。即使所有 SDK 失败，鉴权、文档、健康及不依赖这些 SDK 的路由仍运行。
5. 路由只允许访问配置启用且已就绪的身份。未启用沿用 SERVICE_NOT_ENABLED；已启用但初始化中、失败、关闭或已知工作线程退出，立即返回 SERVICE_NOT_READY，不等待该 SDK，也不初始化或重试登录。
6. TQ 的线程存活/接收任务状态参与可用性判断；readyz 和路由读取这种本地状态，不进行实时网络探测。SDK 内部暂时断网但尚未发现时，仍由正常调用及已有超时发现，不承诺提前判断所有远端故障。

### 实例与资源隔离

CCXT 仅在 load_markets 成功后发布可供路由取得的客户端；初始化失败只移除并关闭本次实例，不关闭其他交易所、模式或市场。注册表短锁只保护登记和取值，不在锁内等待网络。批量初始化入口同样逐项隔离，不保留全体回滚的第二条链路。

TQ 继续在原 TqWorker 线程创建、调用和关闭 SDK；启动协调线程只等待其初始化结果。缓存仍由应用持有，Provider 失败不关闭共享库。CFB HTTP 客户端仍在应用事件循环释放。

应用退出先禁止新业务和新的初始化，再停止后台任务，等待已发起的初始化结束，关闭元数据任务、Provider 和共享缓存。不能在线程尚在初始化时关闭其依赖，不能因晚到的初始化成功把退出中的应用重新标成 ready。重复关闭、启动取消、重复取消和同一运行时重新进入生命周期均须安全。不能强行中断 Python/原生 SDK 初始化；正在执行的 SDK 仍受自身等待规则约束。

### 错误与后台行为

明确的 CCXT 只读网络失败、客户端已关闭、CFB 连接/读取失败及代理超时、TQ 的网络不可用/工作线程未就绪，在 HTTP 层统一为 503 SERVICE_NOT_READY，并带准确 service 身份；不暴露凭据或原始上游异常。

不把行情缺口、非法数据、缺少权限、参数/价格错误和业务拒绝归为服务宕机。已发送操作的 OPERATION_STATUS_UNKNOWN 保留，绝不自动重发写请求；CFB 已收到的上游 HTTP 业务响应继续原样转发。TQ 已有休市缓存兜底先按原逻辑执行，不能因为错误标准化改变其数据流程。普通数据等待超时仍使用原数据错误，不据此永久禁用整个 SDK。

不因单次请求失败永久锁死仍可重试的连接。初始化失败或已退出的 TQ 工作线程需重启进程后重建；本次不添加新的自动恢复调度。后台请求继续使用正式 HTTP 路由；SDK 尚未就绪时按已有单项失败继续和下一轮规则处理，不以全体 SDK 就绪为清理或其他路由的前置条件。

## 公开接口与用户写法

用户原有配置、Just 入口和业务请求参数保持不变。readyz 返回 200 表示 HTTP 应用可服务，新增 services 状态表，例如 TQ 不可用时：

```json
{
  "status": "ready",
  "initialized": ["ccxt/kraken/future/live", "cfb"],
  "services": {
    "tq": "failed",
    "ccxt/kraken/future/live": "ready",
    "cfb": "ready"
  }
}
```

此时有正常鉴权的 `GET /tq/fetch_tick?symbol=KQ.m@SHFE.cu` 立即返回 HTTP 503：

```json
{"detail":{"code":"SERVICE_NOT_READY","service":"tq"}}
```

同一时刻 Kraken 的正常请求仍可成功。Binance 的不可用身份例如 `ccxt/binance/future/live`，CFB 为 `cfb`。未列入白名单仍返回 SERVICE_NOT_ENABLED。进入/退出应用生命周期期间 readyz 返回 503/not_ready，并携带同结构的 initialized、services；healthz 的 status=ok 不变。

## 测试、验证与阶段过渡

- 离线先用可控事件阻塞一个初始化任务，证明 HTTP/其他身份能就绪、故障路由立即拒绝；分别覆盖 TQ、CFB、Binance、Kraken 失败及全体失败。
- 使用真实 ExchangeManager 配合离线 SDK，验证单身份失败不清掉已完成实例，未完成客户端不可发布，其他市场/模式隔离，失败实例关闭且共享缓存不受影响。
- 使用真实 TqWorker 验证初始化失败、消息循环退出、未就绪及关闭状态的 HTTP 拒绝，不返回失效交易状态快照。
- HTTP 测试覆盖 readyz 状态视图、Bearer 鉴权、未启用与未就绪的区别、明确网络错误统一；同时证明上游业务错误、行情完整性、休市缓存及未知订单结果未被误改。
- 更新原来要求串行等待/任一失败全退出的测试；保留资源关闭、初始化取消、重复取消、重新进入、后台首轮/退出和缓存所有权回归。离线测试全部使用临时配置、库及 SDK/HTTP 替身。
- 通过正式入口 `just test`、`just lint`、`just check`。在线验证不进入离线入口；若执行，仍限用户已授权的 live 只读调用，不发送交易操作。
- 本任务在一个 change 中同时切换生命周期、访问检查、健康描述和验证，无长期兼容包装或两套状态真值。
