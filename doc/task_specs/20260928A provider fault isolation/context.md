# SDK 故障隔离

## 使用场景与设计初衷

部署时 TQ 认证连接超时，但 Binance、Kraken 已成功初始化。现有启动器等待全部服务成功，单个 SDK 故障使整个应用无法提供 HTTP，部署脚本随后清理容器。CCXT 注册表还会在一个实例初始化失败时关闭所有交易所实例。

用户需要健康服务继续工作，访问故障服务时得到统一的不可用响应。故障身份仍保留在状态中，不能被伪装成未配置或从白名单静默删除。

## 方案对比

仅捕获异常后继续串行初始化，仍会被长时间不返回的 SDK 阻塞。按身份在独立启动线程中初始化，可以让 HTTP 及其他身份及时就绪，并保留现有 SDK 所属线程和共享缓存所有权。

为每次请求主动探测、引入进程隔离或通用熔断器，会新增重试、恢复和重复下单语义。本次复用现有客户端调用链、有限等待和 SDK 自有恢复能力，不增加这些机制。

## 取舍结论

应用就绪与 SDK 就绪分开。初始化任务受生命周期管理；失败只影响自身身份，关闭仍等待已发起的初始化结束，随后按既有所有权释放资源。路由拦截已知未就绪实例；明确网络不可用也使用统一错误，正常业务拒绝、行情数据完整性和订单结果未知保留各自契约。
