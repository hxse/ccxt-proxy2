# 缓存概况与保留清理

## 使用场景与设计初衷

用户需要知道某条序列最新连续数据的起止和数量，并限制长期积累的磁盘规模。普通行情每条 live 序列保留三万根，sandbox 定期清零；辅助数据按十年独立保留。

只删除旧行会留下错误的 covered_from、空片段或缺失换月上下文。维护必须由缓存模块同时处理数据与证明，脚本只能触发路由。

## 方案对比

独立进程直接写活跃 DuckDB 无法由现有线程锁协调。服务内高级维护入口能复用数据库所有权、事务和锁，也支持用户主动触发。

将保留 K 存成全局隐式默认会与“脚本配置只构造本次请求”冲突。因此概况只报告实际数据，清理结果回显本次规则。

## 取舍结论

分类保留，按序列短事务执行，共用原片段机制并禁止维护重入。逻辑行数和物理文件大小分别表达，不把每小时清理改成整库重建。
