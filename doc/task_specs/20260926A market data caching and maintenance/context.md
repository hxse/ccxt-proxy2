# 行情缓存复用与定期维护

## 使用场景与设计初衷

TQ 实时序列单次最多请求一万根。用户希望按需查询两万根等更长连续历史，同时用后台每小时请求积累数据，重启后能够继续复用本地历史。默认主动保存 28 个品种的主连、加权以及四个周期，普通行情每条 live 序列定期保留三万根。

用户请求与定时请求具有同等地位：谁请求了什么，就通过同一业务入口校验并缓存什么。后台清单只规定主动请求计划，不限制用户接口。后台不维护第二套数据、连续性判断或缺口恢复算法。

项目重点维护上市后的正常数据。上市前相关请求，现有链路能直接处理就处理，处理不了就明确拒绝；不为少见的历史边界增加上市日期查询、起点探测或跨空窗口补拉，也不承诺所有数据源都能返回全部短历史。

现有 DuckDB 已通过有效批次、真实时间戳重叠、segment_id 与 covered_from 保证缓存复用边界。它不依赖相邻时间差猜测期货连续性，应扩展高级入口而不是重写证明机制。

CCXT 已有 since-limit 与 since-latest 缓存流程；latest-limit 尚未读取缓存。三个查询需要复用分页基础并统一取消专门的尾根确认，仍正常返回未知尾根。TQ 则直接使用 SDK 最新窗口，不采用 CCXT 分页或 interval 推算。

日历、逐日主连映射与换月旧价格各有不同的完整性证据。SDK 两类元数据的静态源缓存和本机日期依赖还需要替换，否则长时间运行可能一直使用过期源表。

## 方案对比

直接复用 TQ 内存 serial 能减少重复获取，却不能保存跨进程积累的一万根之外历史。另造数据库或通用 Provider 框架增加了两套身份、锁和连续性逻辑，无法利用现有缓存的成熟边界。

按休市时间提前跳过官方请求会误判实际服务状态。先调用 SDK，失败后只接受明确的真实休市状态，更符合正常 SDK 缓存也可返回数据的事实。

后台按 10、100、1000、一万逐级试探需要额外状态与请求，而 SDK 已复用固定长度序列。每轮直接请求一万根，能重叠就自然续接，不能重叠就保留独立片段，适合常见的停机几天场景。

自动刷新不采用小时 TTL。日历比较官方节假日源实际末日期；映射每次请求重新取得官方历史事件源，再检查本地摘要和完整覆盖。SDK 当前合约资料可能与真实行情和历史源不同步，不能作为历史映射的否决依据。

源表可能预先公布下一交易日的换月事件。生效日期必须由实际行情时间支持，不能仅因周末日历指向下周就启用预公告。当前和历史映射统一来自同一份官方事件源，接受该源自身的发布时效，不再依赖另一套当前标的。每个业务请求固定自己的可信时间，不要求整轮后台构成同一时刻快照。

## 取舍结论

采用共享缓存、分开的 CCXT/TQ 获取算法、高级存储 API、两个 HTTP 后台脚本与单一小时调度。普通 OHLCV 保守不新增持久化网络尾根；过渡利用单次 N＋1 目标窗口确认前 N 根，复用同一个尾根筛选器。

这是有限保留的本地历史方案，不承诺完整镜像、任意停机时长恢复或任意久远旧合约过渡。普通行情按根数保留，日历、映射和过渡独立按年限保留；长期备份由使用者另行安排。

主任务实际整理整套 current spec，明确当前能力和共同职责。尚未实施的设计只属于 task spec；对应实现完成后更新其现行规范，最终再核对跨模块一致性，避免文档提前宣称新能力可用。
